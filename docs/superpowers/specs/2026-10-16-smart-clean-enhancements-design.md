# 智能清理增强（第二阶段）设计文档

日期：2026-10-16
状态：待实现
相关前置：`docs/superpowers/plans/2026-10-16-smart-clean-enhancement.md`（已完成 6 任务）

## 意图与原因

第一阶段已让「智能清理」具备标点/符号/MD/HTML 清理与 5 个开关。本阶段解决
**可信度与可控性**问题：用户按下「智能清理」后无法预知/复核改了什么，容易误清
且不敢使用破坏性较强的步骤（尤其是段落合并）。同时清理规则（符号映射）目前硬编码，
无法按个人/书稿调整；批量清理整本书为逐页串行，速度随书页数线性增长。

## 目标

1. **清理预览 + 一键还原**（F1）：清理前先看将发生的变化与统计，确认后再应用；
   应用后提供明显的「撤销本次清理」入口（复用现有 undo 栈）。
2. **设置内可视化对照表 + 实时预览**（F2）：每个开关下方给出「前 → 后」示例；
   提供一个输入框，实时显示当前开关组合下的清理结果。
3. **可配置符号映射表**（F3）：符号归一映射暴露为配置项，可编辑。
4. **清理报告**（F4）：清理返回每页改动统计（标点/符号/MD/标签/段落合并/字符数），
   前端汇总展示。
5. **更智能的段落合并**（F6）：在「上段结尾无句末标点」基础上，增加列表/缩进/冒号
   引入等屏障判断，减少误合并。
6. **批量清理并行化**（F7）：多页清理用线程池并行，保留输入顺序。

## 非目标

- 不做服务端状态化的「dry-run 会话」：`/api/clean` 保持无状态，预览纯由前端在
  拿到结果后比对生成。
- 不改变清理对表格的原子透传语义；不改变现有 5 个开关的默认值。
- 不引入 asyncio；并行仅用 `concurrent.futures.ThreadPoolExecutor`。

## 反目标（即使技术可用也算失败）

- 预览/报告引入明显卡顿或二次请求风暴（实时预览必须防抖）。
- 符号映射可配置后破坏 `clean(clean(x)) == clean(x)` 幂等性。
- 并行使输出顺序错乱或在不同页间串状态。
- 更智能合并导致「应合并的 OCR 拆段不再合并」的回归。

## 约束

- Python ≥3.11，Windows，stdlib-only（unittest）；无新第三方依赖。
- `configmanage` 配置写入走 `_CFG_LOCK` + `_atomic_write_json`。
- 锁序：config → session → engine/image；清理为纯函数，不触碰 session/engine。
- 无 JS 单测；前端改动以 `node --check ui/app.js` + Python 侧 `_UI_HTML` 断言为准。
- 所有改动保持向后兼容：`clean_page_html` 默认返回原类型（str）。

## 已决定的做法（本设计作出，非用户逐条确认）

- 报告统计在**服务端**计算（可被 Python 单测覆盖），`clean_page_html(with_stats=True)`
  返回 `(html, stats)`。
- 符号映射存入 `ui_settings.clean_symbol_map`（复用既有 `/api/ui_settings` 读写与校验），
  而非新增顶层键与端点。
- 预览模态框在前端渲染；「一键还原」用现有 undo 栈 + 带动作按钮的 toast。
- 并行度 = `min(4, cpu_count)`；单页时同步执行。
